Step-by-Step Module Workflow

Detailed Technical Specification for User Journey & Data Mutations

1

Authentication & Role Selection

Session instantiation and Role-Based Access Control (RBAC) initialization.

Route: /login → auth.py

User Interface Flow

  • User accesses the root application and is intercepted by the FastApi session middleware.
  • Presents login form requiring: Email, Password, and a Role Dropdown.
  • Available Roles: Platform Admin, Migration Analyst, Domain SME, Validation Specialist.

Backend Data Mutation

[POST] /login Payload: { "email": "jeeva@simplicitywealth.com", "role": "Domain SME" } → session_mgr.authenticate() → Sets HttpOnly Cookie: session_id → Redirects to /firm-knowledge

* Note: The selected role governs downstream approvals (e.g., Only "Domain SME" or "Platform Admin" can sign off in Step 6 HITL queue).

2

Firm Knowledge Base Instantiation

Capturing the Discovery Questionnaire to dynamically generate cohort execution waves.

Route: /firm-knowledge → ui/state.py

User Interface Flow

  • Interactive web form replaces traditional file-based discovery.
  • Captures core migration attributes: Target Firm Name, Total Advisor Population, Operating Model (Rep-as-PM), Source Platforms (Amplify/Schwab), and strictly enforced AUM Drift Gate (e.g., 0.50%).
  • File drop zone for uploading supplementary data dictionaries (.json) and transformation rules (.md).

Backend Data Mutation

[POST] /api/knowledge/submit-questionnaire → state_store.update_questionnaire_from_form() // Dynamic Wave Calculation Triggered: Total Reps: 120 Pilot Wave: MIN(5, Total) = 5 Wave 1 (25%): 28 Wave 2 (35%): 40 Wave 3 (Rem): 47 → State generates Dashboard Overview context.
3

Canonical Entity Scope Selection

Decoupling the 15 fixed platform taxonomy elements from migration-specific profiles.

Route: /entity-selection → kernel/wealth_kernel.py

User Interface Flow

  • System loads the immutable Wealth Kernel Taxonomy: 15 fixed entities (e.g., Account, Sleeve, Position, Documents).
  • User interacts with a toggle-based Menu Card to classify each entity's scope for the current migration:
    IN_SCOPE, PHASE_2, ARCHIVE_ONLY, OUT_OF_SCOPE.
  • User clicks "Save Scope Configuration".

Backend Data Mutation

[POST] /api/entities/save-scopes Payload: { "scope_Account": "IN_SCOPE", "scope_Terminated Accounts": "ARCHIVE_ONLY", "scope_Tax Lot": "PHASE_2" } → state_store.save_entity_scopes(scopes_map) → Downstream modules now strictly filter by IN_SCOPE or ARCHIVE_ONLY.
4

Entity Sample File Ingestion

Collecting raw legacy data samples formatted to expected canonical schemas.

Route: /entity-sample-files → storage/

User Interface Flow

  • UI dynamically renders file upload blocks only for entities marked IN_SCOPE or ARCHIVE_ONLY in Step 3.
  • Displays expected canonical schema headers (e.g., ACCT_NUM, CUSTODIAN_CODE, OPEN_DATE) for visual reference.
  • User uploads raw legacy extracts (e.g., `amplify_sleeves.csv`, `accounts.csv`).
  • File card updates to green "PARSED" status showing exact row counts.

Backend Data Mutation

[POST] /api/entities/upload-sample-file → Reads file into Memory (BytesIO) → Uses Pandas to parse CSV & count rows → state_store.attach_entity_sample_file() { "filename": "amplify_sleeves.csv", "row_count": 4, "status": "PARSED" } → Connector classes fall back to these local `test_files/` if Azure storage is disconnected.
5

Canonical Model Building (Agent Pipeline)

Crosswalk mapping, AI inference, and business logic execution to construct target schemas.

Route: /agent-pipeline → agents/orchestrator.py

User Interface Flow

  • User enters Agent Pipeline Studio and clicks "Execute 9-Agent Pipeline".
  • The master orchestrator runs the pipeline. Statuses flip to EXECUTED or PASS.
  • Deep Dive Inspection: User clicks the "Schema Mapper Agent" card to open the slide-out inspector drawer.
  • Inspector shows side-by-side: Raw Source JSON → Editable SQL Crosswalk → Target Canonical Payload.

Backend Data Mutation

[POST] /api/pipeline/run → orchestrator.run_cohort_pipeline() // Sub-Module: SchemaMapperAgent Input (Raw): {"CUST_CODE_SRC": "SCHW"} Logic Applied: VALUE_TRANSFORMS["SCHW" -> "SCHWAB"] Output (Target): {"CUSTODIAN_CODE": "SCHWAB"} // Sub-Module: AzureAIFoundryMapper Input: Unmapped field "EXSTIVA_BILLING_TIER" Call: GPT-4o Zero-shot ChatCompletion Output: Target inferred as "SPARC_Billing__c" → Outputs staged to target data plane adapters.
